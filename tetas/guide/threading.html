Threading & the TickManager ​

The single most important thing to understand about this runtime: there is one main thread, and the TickManager is the cooperative loop that drives it.

TL;DR

The TickManager is not a thread — it's a single-threaded event loop (like JavaScript's) running on the game's main script thread. You can create real .NET threads, but you must never touch the game/host from them; marshal back with RunOnMainThread / await JumpToMainThread() first.

What the TickManager is ​

It is a per-Core scheduler. In its constructor it records the current managed thread as the main thread, and installs a custom SynchronizationContext so that await continuations resume on that thread rather than on a thread-pool thread.

csharp
// TickManager — construction & state
public class TickManager
{
    private ConcurrentQueue<Action> _scheduledActions = new();   // "run next tick"
    private ConcurrentQueue<Action> _backBuffer       = new();   // swapped in each tick
    private readonly PriorityQueue<Action, long> _delayed = new(); // timed work, by Stopwatch ticks
    private readonly Lock _lock = new();
    private readonly int  _mainThread;
    private readonly TickSynchronizationContext _context;

    public TickManager()
    {
        _mainThread = Environment.CurrentManagedThreadId;
        _context = new TickSynchronizationContext(this);
        SynchronizationContext.SetSynchronizationContext(_context);   // await resumes here
    }

    public bool IsMainThread => _mainThread == Environment.CurrentManagedThreadId;
    public void AssertMainThread()
    {
        if (!IsMainThread)
            throw new InvalidOperationException(
                "This function has to be called from the main thread only.");
    }
}

Two data structures do all the work:

  • A lock-free ConcurrentQueue<Action> for "run this on the next tick", double-buffered with a back buffer so it can be drained without blocking producers.
  • A PriorityQueue<Action, long> keyed on Stopwatch timestamps for delayed and repeating work, guarded by a Lock.

The tick pump ​

The host calls Tick() once per frame (via Entrypoint.Tick → Core.TickManager.Tick). Each call drains the scheduled queue, then runs any delayed actions that are now due — all on the main thread, each wrapped so a single throwing action can't break the loop.

csharp
public void Tick()
{
    // 1. atomically swap the live queue with the back buffer (lock-free)
    var queue = Interlocked.Exchange(ref _scheduledActions, _backBuffer);
    while (queue.TryDequeue(out var action))
        TryRun(action);                     // TryRun = try/catch + Log.Error
    _backBuffer = queue;

    // 2. pop every delayed action whose timestamp is due
    long now = Stopwatch.GetTimestamp();
    List<Action>? due = null;
    using (_lock.EnterScope())
        while (_delayed.TryPeek(out var a, out long ts) && ts <= now)
            (due ??= new(8)).Add(_delayed.Dequeue());

    if (due != null)
        foreach (var a in due) TryRun(a);
}

Everything funnels through here

Delay, SetTimeout, SetInterval, NextTick, and every resumed await continuation ultimately runs inside this Tick() call on the main thread. That is why the model is safe without locks around game state: only one thing runs at a time.

Scheduling API ​

You reach the scheduler through the static API (and SharedAPI) facade:

APIMeaning
await API.Delay(ms)Resume after ms. Delay(0) = next frame.
await API.Yield()Give up the rest of this frame; resume next tick (= Delay(0)).
API.SetTimeout(action, ms)Run action once, ms later, on the main thread.
API.SetInterval(action, ms[, startMs])Repeat every ms. Returns an Interval with .Cancel().
API.NextTick(action)Enqueue action for the next tick.
API.RunOnMainThread(action)Run inline if already on main, else enqueue.
await API.JumpToMainThread()ValueTask; completes instantly if on main, else resumes on main.

SetInterval is built on ScheduleRepeated, which re-arms a delayed action after each run and hands you a cancel token:

csharp
TickManager.Interval loop = API.SetInterval(() => DrawHud(), 0);   // every frame
// later:
loop.Cancel();

// one-shot:
API.SetTimeout(() => API.Log.Info("2s later"), 2000);

async / await ​

Because a SynchronizationContext is installed on the main thread, ordinary async/await works and continuations come back to the main thread. This replaces the old Tick += handler pattern with a plain loop:

csharp
public class HudLoop : IScript
{
    public void Initialize()
    {
        _ = RunAsync();               // start an async loop
    }

    private async Task RunAsync()
    {
        while (true)
        {
            DrawHud();                // native calls — safe, we're on main
            await API.Delay(0);       // yield one frame, resume on main
        }
    }
}

Event, command, funcref, and export handlers may all be async; the CallWrapper fire-and-forgets the returned Task and logs faults.

Coming from Lua ​

If your mental model is Citizen.CreateThread and Citizen.Wait, the mapping is nearly one-to-one — because Lua's "threads" are the same idea: cooperatively-scheduled coroutines on the main thread, not real OS threads.

Citizen.CreateThread(fn)an async Task loop, started with _ = Loop();Both run on main; both run up to the first yield immediately.
Citizen.Wait(ms)await API.Delay(ms)—
Wait(0) / Citizen.Wait(0)await API.Yield()Yield one frame.
Citizen.SetTimeout(ms, cb)API.SetTimeout(cb, ms)Arg order flips — action first in .NET.
(hand-rolled loop + Wait)API.SetInterval(action, ms).NET has a real interval primitive with .Cancel().

csharp
// Lua:
//   Citizen.CreateThread(function()
//       while true do
//           DoWork()
//           Citizen.Wait(0)      -- every frame
//       end
//   end)

public class MyScript : IScript
{
    public void Initialize()
    {
        _ = WorkLoop();            // fire-and-forget — the CreateThread equivalent
    }

    private async Task WorkLoop()
    {
        while (true)
        {
            DoWork();              // natives OK — still on the main thread
            await API.Delay(0);    // == Citizen.Wait(0)
        }
    }
}

// A periodic loop is even shorter with SetInterval:
//   Citizen.CreateThread(function() while true do Tick() Citizen.Wait(5000) end end)
API.SetInterval(Tick, 5000);

"Background thread" in Lua isn't a real thread

Citizen.CreateThread gives you concurrency on the main thread, not parallelism — so the faithful port is an async loop, not new Thread / Task.Run. Reach for a real thread only when you want genuine parallelism for work that never touches the game (next section) — something Lua can't do at all.

Can you create new threads? ​

Yes. This is real .NET 10 with the full BCL — new Thread(...), Task.Run(...), ThreadPool, Parallel, and channels all work and really do run on separate OS threads.

But you may not touch the game/host from them. Natives, entity access, and event emission are main-thread-only:

  • Emitting (EmitLocal/EmitServer/EmitClient) calls AssertMainThread() and throws off-thread.
  • Natives use a per-context pointer that is only valid on the main thread (see Native bridge).
  • The custom SynchronizationContext exists only on the main thread. If you start work with Task.Run, its continuations run on the pool — they will not automatically return to main.
csharp
// background work, done right
public async Task ProcessBigFile(string path)
{
    // heavy, no game access — fine on a pool thread:
    string[] lines = await Task.Run(() => File.ReadAllLines(path));
    var parsed = await Task.Run(() => Parse(lines));

    // hop back before touching anything game-related:
    await API.JumpToMainThread();
    API.EmitLocal("myresource:parsed", parsed.Length);   // now safe
}

The classic mistake

Calling a Native.* or an Emit* from inside Task.Run, a raw Thread, a timer callback, or a library's async continuation. It will throw "…called from the main thread only" or corrupt the native context. Always marshal back first.

Getting back to the main thread ​

API.RunOnMainThread(action) Runs action immediately if you're already on main; otherwise enqueues it for the next tick. (ScheduleIfBackground internally.)

await API.JumpToMainThread() Returns a ValueTask that is already completed on main, or resumes your method on the main thread on the next tick. The idiomatic "hop back" inside an async method.

API.NextTick(action) / API.SetTimeout(action, ms) Explicitly queue a callback onto the main-thread loop.

The runtime itself uses this pattern: async cross-boundary results (AsyncRetVal) marshal their completions back with ScheduleIfBackground before invoking your callback — see Serialization → async return values.

Rules of thumb ​

  • Prefer the cooperative model. An async loop with await API.Delay(ms) covers almost every "background" need and never leaves the main thread.
  • Use real threads only for CPU-bound or blocking work that does not call into the game (parsing, crypto, file/HTTP I/O via non-CFX APIs). Marshal results back with JumpToMainThread.
  • Long loops should yield. A while (true) with no await Delay will block the tick and freeze the resource — always yield at least one frame.
  • Don't over-schedule. SetInterval(fn, 0) runs every frame; use a real interval (e.g. 250 ms) for anything that doesn't need per-frame updates.
