Entities & pools ​

Entities are thin wrappers over an integer handle. Pools hand out one stable wrapper per handle and keep them in sync with the engine.

Getting entities ​

csharp
// Get(handle)         → existing wrapper or null
// GetOrCreate(handle) → existing, or a freshly-pooled wrapper (validated)
Vehicle veh = API.Vehicles.GetOrCreate(handle);
veh.Position = new Vector3(0, 0, 72);
veh.Velocity = Vector3.Zero;
int hp = veh.Health;

// players resolve from a server id and expose their ped:
Player p   = API.Players.Get(source);   // server id → Player
Ped?   ped = p.Ped;                      // null if no ped
Vector3 at = p.Position;

A pool guarantees identity: ask for the same handle twice and you get the same object, so you can attach state to a wrapper and find it again later.

Entity interfaces ​

The side-agnostic contracts live in CitizenFX.FiveM.Shared.Entities. Concrete classes are per-side and implement the relevant ones.

csharp
public interface IEntity            { int Handle { get; }  bool Exists { get; } }
public interface INetworkedEntity : IEntity { int NetworkHandle { get; } }

public interface ISharedWorldEntity : IEntity
{
    Vector3 Position { get; }  Vector3 Velocity { get; }  float Speed { get; }
    Vector3 Rotation { get; }  Vector3 RotationVelocity { get; }  float Heading { get; }
    int Health { get; }  int MaxHealth { get; }  uint Model { get; }
}

public interface ISharedPlayer  : IEntity            { string Name { get; } }
public interface ISharedProp    : ISharedWorldEntity { }
public interface ISharedBlip    : IEntity            { int Sprite { set; } }
public interface ISharedPed     : ISharedWorldEntity { /* weapons, armour, ragdoll, appearance… */ }
public interface ISharedVehicle : ISharedWorldEntity { /* colors, health, doors, neon, plate… */ }

ISharedVehicle and ISharedPed are rich — vehicles expose colors (as ColorRGB records), body/engine health, door lock status, neon, number plate, and tuple getters like GetColors(); peds expose weapons, armour, component/prop variation, head blend/overlays, and ragdoll control. The concrete per-side classes implement these over the appropriate natives.

csharp
// Data records used by entities
public record ColorRGB(int R, int G, int B);
public record ColorRGBA(int R, int G, int B, int A);

Pool internals ​

Pools are generic over <TEntity, THandle>. The base pool is a Dictionary<THandle, TEntity> plus a factory; GetOrCreate validates and caches.

csharp
public abstract class BasePool<TEntity, THandle>(Func<THandle, TEntity> factory)
    : IPool<TEntity, THandle> where TEntity : IEntity where THandle : notnull
{
    protected virtual bool ValidateHandle(THandle handle) => true;

    public virtual TEntity? Get(THandle handle) => Pool.GetValueOrDefault(handle);

    public virtual TEntity? GetOrCreate(THandle handle)
    {
        if (Pool.TryGetValue(handle, out var e)) return e;
        if (!ValidateHandle(handle))            return default;
        var created = Factory(handle);
        if (created is null)                    return default;
        return Pool[handle] = created;
    }
}
  • IPool<TEntity,THandle> — Get / GetOrCreate.
  • INetworkedPool<TEntity,THandle> adds NetworkHandleToLocal / LocalHandleToNetwork — the mapping used for networked serialization.
  • CheckingPool<TEntity,THandle> adds Cleanup(), which removes wrappers whose Exists is now false. The client blip pool is cleaned on a timer.

Engine lifecycle ​

The pools are wired to engine events so wrappers appear and disappear with the entities they track.

csharp
// ServerPools — entity routing
API.OnEvent("entityCreated", new Action<int>(OnEntityCreated));
API.OnEvent("entityRemoved", new Action<int>(OnEntityRemoved));

private void OnEntityCreated(int handle)
{
    switch (Native.GetEntityType(handle))   // 1 ped · 2 vehicle · 3 object
    {
        case 1: Peds.GetOrCreate(handle);     break;
        case 2: Vehicles.GetOrCreate(handle); break;
        case 3: Props.GetOrCreate(handle);    break;
    }
}

On the client, ClientPools additionally initializes the local player, runs a per-frame tick to render markers, and periodically cleans up blips:

csharp
// ClientPools ctor (abridged)
Players.InitLocal();
API.SetInterval(Cleanup, 4000);   // blip cleanup
API.SetInterval(Tick, 0);         // marker render, every frame

Markers & checkpoints (client) ​

Markers are a client-only, managed concept — not a game entity handle but a description the pool renders each frame. A Marker carries position, type, scale, a ColorRGBA, render distance, rotation/direction, texture dict/name, and flags (bounce, face-camera, invert…).

csharp
public class Marker
{
    public int Handle { get; }
    public bool Exists => API.Pools.Markers.Exists(Handle);
    public int Type { get; set; }
    public Vector3 Position { get; set; }
    public Vector3 Scale { get; set; }
    public ColorRGBA Color { get; set; }     // defaults to opaque white
    public int RenderDistance { get; set; }  // also maintains RenderDistanceSquare
    public string? TextureDict { get; set; }
    public string? TextureName { get; set; }
    public bool Bounce, FaceCamera, Rotate, Invert;
}

Entities on the wire ​

When an entity crosses a boundary, MessagePack pool formatters convert it to an id and resolve it back to a pooled wrapper on the other side. The two profiles differ:

  • Local (PoolFormatter): serializes entity.Handle directly; a nil is written if the entity is null or no longer exists.
  • Remote (RemotePoolFormatter): serializes LocalHandleToNetwork(handle) (a network id), and on read maps it back with NetworkHandleToLocal before GetOrCreate.

That's why a server handler taking ISharedPlayer "just works" — the source id and any entity args are resolved through the pools. Full detail on the Serialization page.
